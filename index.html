CampusGuard

A security-focused campus marketplace prototype for verified students. Built with a Next.js frontend, FastAPI backend, and PostgreSQL data layer, with university-email verification, chat, and a two-pass scam-analysis pipeline combining heuristic checks with AI-assisted review.

Next.js + ReactFastAPIPostgreSQLScam analysis
EXPLORE THE BUILD +

Identity and access. University-email verification links accounts to campuses; the authentication service includes password hashing and verification-token handling.

Detection pipeline. Heuristic analysis provides an initial risk assessment, with a deeper AI-assisted analysis path and asynchronous worker code.

Application architecture. The application combines marketplace listings and chat APIs with a PostgreSQL schema and Alembic migrations.

THE SECURITY PROBLEM +

Purpose. CampusGuard explores a practical question: how can a campus marketplace help students recognize suspicious listings before they decide to engage? The prototype brings account verification and scam-risk review into the same experience.

Security perspective. University-email verification and listing analysis address different concerns. A campus-linked account provides identity context, while a risk assessment helps a user evaluate a particular listing. Neither should be treated as a guarantee that a transaction is safe.

Project boundary. The interface uses sample scan data. This is a prototype for exploring application security and user decisions; it does not establish measured scam-detection accuracy.

02ENTERPRISE NETWORK DEFENSE
VIEW FULL SCREEN ↗

Layered Enterprise Network

A 13-week enterprise security capstone connecting five segmented network zones, Palo Alto and FortiGate firewalls, identity-based access, and SOC monitoring. Built and tested across four phases, from network defense to automated incident response.

Palo Alto + FortiGate5 network zonesSite-to-site VPN
ARCHITECTURE & LESSONS +

The challenge. Make public-facing services available while controlling how traffic reaches internal systems. I divided the lab into outside, DMZ, inside, secure, and firewall-interconnect zones, then configured routing, NAT/PAT, and policies between them.

What I built. Two web servers in the DMZ supported load balancing and failover. Palo Alto and FortiGate firewalls provided separate layers of control, while access restrictions helped limit exposure of Active Directory.

What I learned. Connectivity is only one part of a working security design. Segmentation, identity, monitoring, and response need to work together, and simulated attacks provide a way to check those assumptions.

Reconstructing a Domain Compromise

A full SOC investigation of the simulated ACMEONIONS domain compromise. Reconstructed a multi-stage attack, authored a SIGMA detection rule, and delivered a formal incident response report with remediation recommendations.

Also documented: a sanitized inbound alert involving a hidden environment file. Its ticket records a false-positive disposition; the public summary does not establish whether access succeeded.

Incident reconstructionSIGMAIR reporting
HOW I APPROACH AN ALERT +

Start with context. I work from the alert toward the surrounding activity: which systems communicated, what protocol was involved, when the events occurred, and what related logs can explain the behavior.

Build the explanation. In my Security Onion investigations, I practice comparing Suricata alerts with Zeek connection, DNS, and HTTP records where available. I organize reports around the five W’s, supporting evidence, recommendations, and a conclusion.

Respect the limits. An alert is a starting point. I distinguish observed behavior from possible explanations and leave a finding inconclusive when the available evidence does not support a stronger verdict.

From Detection to Response

Centralized firewall syslog, IIS logs, Security Onion alerts, and Sysmon telemetry in Splunk. Built detections for brute force, scanning, suspicious URLs, and beaconing, then connected alerts to an n8n workflow for threat-intelligence enrichment and Palo Alto firewall blocking. Validated in simulated attacks.

Splunk + Sysmonn8nThreat intelligence
FOLLOW THE RESPONSE WORKFLOW +

Collect and connect. Firewall, web-server, network, and endpoint records each describe a different part of an event. Bringing them into Splunk let me examine activity across those sources and build detections around specific behaviors.

Enrich and act. The n8n workflow extracts a source IP from a Splunk alert, adds GeoIP and threat-intelligence context, and can submit a block through the Palo Alto API. I built it with assistance from Claude Code.

Validate in the lab. Simulated scanning and web attacks against the DMZ triggered detections and exercised the response workflow. This is a capstone lab result; operational use would require further tuning and review of blocking decisions.

Identity Before Access

Implemented SSL VPN with Duo MFA authentication across four network segments. The capstone also included 802.1X, Active Directory integration, and a Guacamole gateway for browser-based access. Audited permissions and enforced least privilege.

SSL VPNDuo MFALeast privilege
ACCESS DESIGN IN PRACTICE +

The objective. Give users a practical route to the resources they need while keeping access tied to identity and permissions. VPN connectivity, authentication, and authorization each play a part in that design.

The implementation. I combined Active Directory integration, Duo MFA, and SSL VPN with network access controls and a Guacamole gateway. The work helped me connect identity decisions with the network paths available to a user.
